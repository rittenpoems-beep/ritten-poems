01Varve / 记忆系统

会话结束之后，
它还记得。

Varve 是一个 AI Agent 的跨会话记忆系统。我独立主导设计，借助 AI 编程工具实现并开源：Python + SQLite FTS5 + PowerShell，MIT 许可，仍在持续迭代。

GitHub 仓库 ↗
4,539会话请求
630 轮对话 · 23,988 条轨迹记录
≈14亿累计输入 token
96%Prompt 缓存命中率
尾部追加注入的直接收益
97.6 MB本地 SQLite 库
可随时重建

以上不是示意数据：它来自我在自己的开发环境里连续使用的真实量级，索引规模、库大小与审计结果仍随使用增长。代码与最新状态见 rittenpoems-beep/varve。

AI 编码助手最消耗人的地方，不是它不会写代码，而是它不记得。会话一结束，之前建立的环境认知、项目状态、做过哪些判断全部丢失；下一次要么重新解释一遍，要么把大段历史重新塞进上下文——既贵又慢，还容易塞进无关内容干扰判断。而当你想回头查“这个决定是在哪一步做出的”，历史信息又很难定位。

Varve 把 Agent 需要记住的东西分成三层，各管各的事，各自用不同的方式存取。环境层记录外部世界的稳定事实，状态层记录当前正在进行的局面，历史层保留发生过的对话和工具轨迹，可以按需检索回来。

名字来自地质学里的纹泥沉积：一年一层，不断累积，可以回溯，旧的层不会被抹掉。

项目原则：只追加 · 可重建 · 可定位

关键实现

  • 环境 / 状态 / 历史三层记忆结构
  • 只注入最新一条状态快照，细节按需检索，不一次灌几十万 token
  • 注入落在请求尾部，不碰固定前缀，因此不破坏 prompt 缓存
  • SQLite FTS5 全文索引 + 多变体检索，可回溯到原文行号
  • 多会话并发写文件：staging 三段式——提案 → 裁决 → 原子提交
  • 全局状态卡：任何目录共用一张，跨工作区、跨框架
  • 零 LLM 调用、零第三方依赖（Python 标准库 + PowerShell 7）
  • 索引层带审计与可执行回归用例

三层结构 · 简化示意

环境 Environment相对稳定的事实：项目结构、依赖、约定、外部系统。变化慢，检索成本低。
状态 State当前局面：正在做什么、试过了什么、结论是什么。以尾部追加的方式注入。
历史 History完整发生过的对话与工具轨迹，索引进 FTS5，需要时定位回来，不需要时不占上下文。

这套划分带来的直接好处是：不用为了“让它想起来”而把整段历史重播一遍，也不必依赖额外的大模型调用来做记忆整理。

兼容性（以仓库 README 为准）

  • Codex：已适配，且经过端到端实测
  • Claude Code：已适配，脚本层验证通过；历史检索尚未接入
  • 只能改写固定前缀来注入记忆的框架：不支持
  • 没有 hook 通道的框架：不支持

我知道它还不好的地方

  • 历史层依赖 ~/.codex/sessions/**/*.jsonl，换了目录结构就得自己改
  • 脚本按 Windows / PowerShell 7 优先写，其他环境没有同等验证
  • 全局状态卡只有一张，不按项目隔离，多项目并行时会互相干扰
  • 首次使用需要手动点一次信任全局 hooks
  • 关键词检索是逐字匹配，换个说法就捞不到；语义索引还在权衡，当前“锚优先 + 覆盖自述”是权宜解法

为什么要把限制写在官网上。一个还没做完的东西，最容易的做法是只讲设计意图、不讲边界。但我在课上要对学生说“这里你可以这样判断”，那我就得先把自己项目的判断依据和失败面摊开。具体行为与最新版本请以 GitHub 仓库 为准。

为什么一个教育者要做记忆系统

因为“Agent 为什么会忘事、上下文为什么有成本”是我课上最难讲清的一块。只有真的把它当成工程问题解决过，我才敢在学生面前说：这里你可以这样判断。

这个项目说明了什么能力

对 Agent 记忆机制、系统结构、上下文管理和工程设计的实际理解；也包括一套不算轻松的工作方式——用 AI 编程工具实现，同时自己守住架构决策和验证标准。

02Workflow / 工作流

把重复劳动
变成结构，
把时间留给判断。

我发布过不少 AI 科普视频，很快就撞上一个问题：真正耗时的不是“想清楚讲什么”，而是围绕它的大量重复操作。

转写、校对、对齐时间轴、按内容切段、生成字幕、准备素材、编排画面、渲染合成——这些环节单个都不难，但它们叠在一起，就会把创作时间挤到只剩零头。

我的做法是把整个生产过程结构化，划成一段段可以独立处理的环节，然后让 Agent 和相关工具承担其中规则明确的部分。人保留的是最需要判断力的环节：讲什么、怎么讲、结果对不对。

这件事本身也是一个很好的教学案例。它不属于“用 AI 写点什么”，而是“用 AI 改造一条生产线”，需要工作流设计、媒体处理、时间轴精度和大量验证——这些恰好是讲给学习者听时最有用的部分：每一步都可能出错，也每一步都能检查。

部分环节已经在真实内容制作中测试使用，但它不是一个成熟的商业软件产品。我不把它包装成产品，也不宣称已经全流程自动化。

生产环节

  • 视频脚本处理
  • ASR 语音识别
  • 字幕与词级时间轴
  • 内容结构化分析
  • 视觉信息规划
  • Motion Design
  • 画面与动画编排
  • FFmpeg 媒体处理
  • 音频与 BGM
  • 视频渲染与自动化处理

用过的工具，和从它们身上学到的

Claude Code、Codex、DeepSeek 相关的 Agent 系统、ComfyUI 是我长期使用的几类工具。它们给我的不是“会操作某软件”，而是几个反复出现的认识：上下文是有限资源，工具描述质量直接决定 Agent 上限，自动化最难的部分是验证而不是执行，以及不同模型在同一任务上的差异远比榜单上显示的更大。

04Path / 路径

我的技术学习
是怎么发生的。

我的专业是数据科学与大数据技术，目前还在本科阶段。但我不是沿着传统程序员的培养路径成长起来的。

我的学习主要来自实际问题、自主研究、读技术文档、做项目实验，以及与 AI 编程工具协作。

这种路径有一个明显好处——我是真的靠 AI 把不会的东西变成能用的能力，所以我非常清楚它在哪里帮得上、在哪里会把你带沟里去。这也是我教学时最有说服力的部分，因为我的卡点和学习者的卡点几乎一模一样。

我也并不认为传统计算机知识因此变得不重要。恰恰相反：当执行变得便宜，问题理解、架构设计、判断力和结果验证的要求被放大了。工具不会替你承担这些。
